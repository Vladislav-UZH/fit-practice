## Робочий порядок

1. Використовувати `REPORT_PLAN.md` як узгоджений план документа.
2. Під час написання перевіряти факти за `CURRENT_STATE.md`, `package.json`, конфігурацією, API та CI.
3. Не описувати незавершені перевірки як завершені.
4. Після злиття фінального аудиту повторно звірити підрозділи 2.5 і 2.6.
5. Для Word використовувати готові SVG-версії рисунків; PNG створювати лише як резерв для несумісного редактора.
6. Сформувати автоматичний зміст, підписи та перехресні посилання у Word.
7. Перевірити підсумковий обсяг: не більше 20 сторінок.

## Межі паралельної роботи

Матеріали звіту зберігаються лише в `docs/practice-report/`. Під час паралельної розробки застосунку не змінювати файли `app/`, `content/`, `server/`, `shared/`, `tests/` і конфігурацію без окремого завдання.

## Контрольні точки після фінального аудиту

У розділі 2 треба оновити лише змінні результати:

- остаточний статус продуктових SVG або адаптивних AVIF/WebP;
- результати screen-reader, keyboard-only і 200% zoom перевірок;
- формальну перевірку контрасту;
- LCP і CLS;
- кількість unit/Nuxt runtime та Playwright тестів;
- остаточне рішення про готовність застосунку без deployment.

## Наступні дії

- після завершення PR фінального аудиту оновити змінні результати в розділі 2;
- сформувати загальні висновки;
- перевірити остаточний список джерел;
- зібрати повний DOCX і втримати обсяг у межах 20 сторінок.
